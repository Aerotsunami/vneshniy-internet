# Архитектура

## Почему архив хранится в Git

Для ежедневного выпуска не нужна отдельная база данных. JSON-файлы в репозитории дают:

- историю правок и быстрый откат;
- резервную копию вместе с исходным кодом;
- проверку данных до публикации;
- работу GitHub Pages без сервера, секретов и регулярного обслуживания;
- понятный интерфейс для автоматизации: один новый файл на один выпуск.

GitHub становится источником истины. `public/archive.json` — производный индекс, который создается при сборке и не редактируется вручную.

## Публикация

Изменение в основной ветке запускает `.github/workflows/deploy.yml`. Процесс устанавливает зафиксированные зависимости, проверяет все выпуски, собирает приложение и публикует папку `dist` в GitHub Pages.

Pull request проходит такую же проверку без публикации. Некорректная дата, пустой текст, HTTP-ссылка, повторяющийся идентификатор или слишком большое число AI-материалов остановят сборку.

## Работа без сети

Service Worker использует три режима:

- навигация — сначала сеть, затем сохраненная оболочка;
- `archive.json` — сразу сохраненная версия и фоновое обновление;
- версионированные ресурсы — сначала кэш, затем сеть.

Первый визит требует сети. После него приложение, интерфейс и открытый архив доступны офлайн. При новой сборке пользователь получает предложение обновиться.

## Масштабирование

Текущая схема рассчитана на несколько тысяч материалов. Если единый индекс станет тяжелее примерно 3–5 МБ, сборку можно разделить на индекс выпусков и отдельные JSON-файлы по годам без изменения исходного формата.

Отдельная база понадобится только при появлении совместного редактирования в реальном времени, приватных выпусков или пользовательских аккаунтов. До этого она добавит больше отказов и расходов, чем пользы.
